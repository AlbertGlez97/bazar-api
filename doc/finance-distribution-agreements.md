# Finance distribution agreements (Phase 5.5)

A distribution agreement ("Acuerdo de reparto") is a persisted, immutable and auditable record of a distribution simulation that the participants accepted. It is created from `POST /api/v1/finance/distribution-simulations` data and can be read, listed and voided afterwards.

## What it is NOT

- It is not a payment, withdrawal, settlement or transfer, and it creates no debt, obligation or member balance. No `Payment`, `Settlement`, `Withdrawal` or `AgreementPayment` table exists.
- It is not a legal contract and carries no digital signature. The document says so in its `notice`.
- It generates and stores no PDF and does not work offline: the frontend renders the JSON and may print it.
- The simulator stays pure: `POST /finance/distribution-simulations` persists nothing, ever. The only new field it returns is `simulationFingerprint`.
- Aportaciones, gastos, jornadas, reservas and ventas are untouched and are never modified by an agreement.

All routes are socio-only (`SocioGuard`): colaboradores, inactive members, foreign members and unauthorized devices get `403`, anonymous callers `401`. The tenant always comes from the account; clients never send `contextId`.

## Flow for the frontend

1. Simulate: `POST /finance/distribution-simulations` and keep `simulationFingerprint` from the response.
2. The participants review the result. The user types a `title` (and optionally a `note`).
3. Create: `POST /finance/distribution-agreements` with the SAME `from`, `to`, `requestedAmountMinor`, `partnerShareBps`, `workShareBps`, `workBasis` and that `simulationFingerprint`. The server recomputes the simulation inside its own snapshot; it never trusts client figures.
4. If the data changed in between the server answers `409 FINANCE_AGREEMENT_SIMULATION_CHANGED` and saves nothing: simulate again, let the participants confirm, create again.

## Simulation fingerprint

`simulationFingerprint = "sim1:" + sha256hex(canonicalJson({period, currency, financialBase, rule, pools, members, totals, warnings}))`. Canonical JSON sorts object keys recursively (key order is irrelevant), keeps array order and rejects `undefined`/non-finite numbers. It excludes itself, `simulation`, `persisted` and any timestamp, so identical data always yields the same value. Any change to the period, rule, pools, a member (including renaming), a warning or a total changes it.

## Create

`POST /api/v1/finance/distribution-agreements` (strict body: unknown properties are `400`).

| Field                             | Rule                                                                                   |
| --------------------------------- | -------------------------------------------------------------------------------------- |
| `id`                              | UUIDv7 generated by the client; the idempotency key                                    |
| `from`, `to`                      | Strict `YYYY-MM-DD`, `from < to` (same as the simulator)                               |
| `requestedAmountMinor`            | Integer `1..2147483647`                                                                |
| `partnerShareBps`, `workShareBps` | Integers `0..10000` that sum to `10000` (otherwise `400`)                              |
| `workBasis`                       | `WORK_SHIFTS` or `KNOWN_MINUTES`                                                       |
| `title`                           | Trimmed, 1..120 characters                                                             |
| `note`                            | Optional or `null`; trimmed, at most 1000 characters; a blank note is stored as `""`   |
| `simulationFingerprint`           | Must match `^sim1:[0-9a-f]{64}$`                                                       |
| `replacesAgreementId`             | Optional or `null`; UUIDv7 of a voided, not yet replaced agreement of the same context |
| `occurredAt`                      | ISO-8601 instant with `Z` or an offset; normalized to UTC                              |
| `createdByMemberId`, `deviceId`   | MUST equal the caller's `x-member-id` / `x-device-id` selection, otherwise `403`       |

Rejected with `400` if present: `contextId`, `createdByAccountId`, `folio`, `status`, `participants`, `members`, `pools`, `totals`, amounts per member or any other unknown property.

Responses: `201` the first time, `200` for an exact replay (same id and same content from the same account) with the original stored document. A replay is answered BEFORE drift detection and never consumes a folio, so a retry after a lost response always works, even if the data changed meanwhile. JSON key order of a replay can differ from the first response (it is read back from JSONB); compare by value.

### Document of record (the response body)

```ts
interface DistributionAgreement {
  id: string;
  contextId: string;
  folio: string; // "AC-2026-00001"
  status: 'active' | 'voided'; // creation always answers 'active'
  title: string;
  note: string | null;
  replacesAgreementId: string | null;
  replacesAgreement: { id: string; folio: string } | null;
  generatedFrom: 'DISTRIBUTION_SIMULATOR';
  algorithmVersion: 1;
  notice: string; // "Documento generado a partir de una simulación aceptada por los participantes. No es un contrato legal ni registra pagos."
  period: {
    from;
    to;
    fromInstant;
    toInstant;
    utcOffsetMinutes: -360;
    interval: '[from,to)';
  };
  currency: 'MXN';
  financialBase: {
    potentiallyAvailableMinor;
    requestedAmountMinor;
    remainingAvailableMinor;
    status: 'complete' | 'partial';
  };
  rule: { partnerShareBps; workShareBps; workBasis; partnerMode: 'EQUAL' };
  pools: { partnerPoolMinor: number; workPoolMinor: number };
  participants: {
    memberId;
    name;
    role: 'socio' | 'colaborador';
    isActive;
    partnerEligible;
    partnerAmountMinor;
    workUnits;
    shiftCount;
    knownMinutes;
    unknownDurationCount;
    workAmountMinor;
    totalMinor;
  }[];
  totals: { distributedMinor: number; undistributedMinor: number };
  warnings: { code: string; message: string }[]; // SIMULATION_ONLY and NOT_A_PAYMENT_OR_OBLIGATION are removed
  simulationFingerprint: string;
  snapshotFingerprint: string; // sha256 hex of the canonical document without snapshotFingerprint/status/reversal/replacedBy
  occurredAt: string; // UTC ISO
  receivedAt: string; // server clock, UTC ISO
  createdBy: {
    memberId: string;
    name: string;
    accountId: string;
    deviceId: string;
  };
  reversal: null; // live projection, see the detail endpoint
  replacedBy: null;
}
```

Member names, roles and flags are frozen: renaming or deactivating a member later never changes the document. All amounts are integer minor units.

### Errors

| Status | `code`                                                                               | When                                                                                       |
| ------ | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| 400    | (Nest default)                                                                       | Validation, malformed ids                                                                  |
| 403    | (Nest default)                                                                       | Not a socio, origin mismatch, revoked device                                               |
| 404    | (Nest default)                                                                       | The id collides with a record this tenant cannot see (never disclosed)                     |
| 409    | `FINANCE_AGREEMENT_ID_CONFLICT`                                                      | The id exists with different content or was created by another account                     |
| 409    | `FINANCE_AGREEMENT_SIMULATION_CHANGED`                                               | Drift; body adds `currentSimulationFingerprint`. Nothing is persisted and no folio is used |
| 422    | `FINANCE_AGREEMENT_REPLACEMENT_INVALID`                                              | Replaced agreement unknown, still active, or already replaced                              |
| 422    | `FINANCE_DISTRIBUTION_EXCEEDS_AVAILABLE`, `_NO_WORK`, `_NO_PARTNERS`, overview codes | Simulator domain errors, propagated unchanged                                              |
| 503    | `FINANCE_AGREEMENT_BUSY`                                                             | Concurrent activity exhausted the bounded retries; safe to retry the same request          |

Domain errors use `{ code, message }`; branch on `code`. Messages are informational English.

## Folio

`AC-<YYYY>-<number>`, where the number is zero-padded to at least 5 digits (`AC-2026-00001`, `AC-2026-100000` after 99999). The year is the business-timezone (UTC-6) year of the SERVER `receivedAt`. Each context and year has its own gapless sequence allocated by an atomic `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` inside the creating transaction (never `count + 1`). A failed creation rolls the increment back, so numbers have no gaps. The folio is unique per context.

## Concurrency

Creation runs in one `RepeatableRead` transaction: live authorization (`FOR SHARE` on account, socio and device), a transaction-scoped advisory lock on the id, replay lookup, replacement check, re-simulation, drift check, folio allocation, inserts. Creations of one context are queued inside the API process, and the whole transaction (re-simulation included) is retried up to 5 times, with a small jittered backoff, on a serialization failure (`40001`/`P2034`) caused by another API instance; if still contended the answer is `503 FINANCE_AGREEMENT_BUSY`.

## Read

- `GET /finance/distribution-agreements/:id` returns the frozen document plus the live projection: `status` (`active|voided`), `reversal` (`{id, agreementId, reason, occurredAt, receivedAt, createdByMemberId, createdByAccountId, deviceId}` or `null`) and `replacedBy` (`{id, folio}` or `null`). A voided agreement is served unchanged; its document stays viewable and printable. Unknown or foreign ids are `404 Agreement not found`; malformed ids `400`.
- `GET /finance/distribution-agreements` lists summaries newest first (`receivedAt desc, id desc`). Query: `from` and `to` together (exact period match, `from < to`), `status` (`active` default or `voided`), `folio` (exact, case-insensitive), `limit` (`1..100`, digits only, default 20), `cursor` (opaque, bound to the context and filters; a tampered or foreign cursor is `400`). Response `{ items, nextCursor }`. Item: `id, folio, status, title, note, from, to, requestedAmountMinor, partnerShareBps, workShareBps, workBasis, financialStatus, distributedMinor, participantCount, occurredAt, receivedAt, replacesAgreement {id, folio} | null, voidedAt | null` (`voidedAt` is the reversal's `occurredAt`). Fingerprints and stored receipts are never listed.

## Void (reversal)

`POST /finance/distribution-agreements/:id/reversals` with `{ id (UUIDv7, different from the agreement id), reason (trimmed, 1..1000), occurredAt, createdByMemberId, deviceId }`. `201` first time, `200` replay of the same reversal, `409 FINANCE_AGREEMENT_ID_CONFLICT` if the reversal id exists with different content, `409 FINANCE_AGREEMENT_ALREADY_VOIDED` if the agreement was already voided by another reversal, `404` for unknown or foreign agreements. The receipt is `{ id, agreementId, reason, occurredAt, createdByMemberId, deviceId, contextId, createdByAccountId, receivedAt, original }` where `original` is the frozen agreement document. Voiding never modifies the agreement row.

To correct an agreement: void it, simulate again, and create a new one with `replacesAgreementId` pointing at the voided one. Each voided agreement can be replaced once; the old document then shows `replacedBy` and the new one `replacesAgreement`.

## Storage, RLS and immutability

Migration `20261009120000_finance_distribution_agreements` creates `DistributionAgreement`, `DistributionAgreementParticipant`, `DistributionAgreementReversal` and `DistributionAgreementCounter`.

- Every id is a UUIDv7 (CHECK). Money is integer minor units with CHECKs: shares `0..10000` summing to `10000`, pools sum to the requested amount, distributed plus undistributed equals the requested amount, participant partner plus work equals the total.
- Composite foreign keys `(id, contextId)` to `Member`, `Account` and `Device` (`ON DELETE RESTRICT`) keep every row inside its tenant.
- `ENABLE` and `FORCE ROW LEVEL SECURITY` with the `tenant_isolation` policy on all four tables.
- Immutability: `BEFORE UPDATE OR DELETE` triggers on the agreement, participant and reversal tables raise `distribution agreements are immutable`. The runtime role keeps its table grants (the provisioner re-grants them on every start), so triggers, not REVOKE, are the guard. The counter table is mutable by design. The service never updates or deletes agreement rows.
- Tests delete their fixtures through `test/agreement-cleanup.ts`, which connects as the owner of the isolated `bazar_test` database and disables the triggers inside a single transaction.

## Known limits

- Eligibility inherits the simulator's current-state rule (no membership history).
- Two agreements may exist for the same period and amount; nothing forbids it. Void and replace to correct.
- Only `MXN`, `EQUAL` partner mode and algorithm version 1 exist.
- The agreement records acceptance of a calculation; it does not prove that money moved.
