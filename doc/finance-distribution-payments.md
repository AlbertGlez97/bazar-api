# Finance distribution payments (Phase 6, backend)

A distribution payment records money that was REALLY PAID against one participant of a distribution agreement. La Marchanta does not move money: it records what was agreed, what was actually paid and what is still pending. "Agreed" is never "paid".

Payments are immutable. A mistake is corrected by a reversal followed by a new payment, never by editing or deleting a row.

All routes sit under `/api/v1`, are socio-only (`SocioGuard`: active socio on an authorized device) and need a JWT plus `x-member-id` and `x-device-id`. Collaborators get `403` on every route, anonymous callers `401`. The context and account always come from the session.

## Source of truth

- Agreed: `DistributionAgreementParticipant.totalMinor` (frozen when the agreement was created).
- Paid: sum of `amountMinor` of the participant's payments WITHOUT a reversal.
- Pending: agreed - paid. Always computed on read, never stored.

## Derived statuses (never stored)

| Level | Value | Rule |
| --- | --- | --- |
| Participant | `UNPAID` | paid = 0 |
| Participant | `PARTIALLY_PAID` | 0 < paid < agreed |
| Participant | `PAID` | paid = agreed |
| Participant | `NOT_DUE` | agreed = 0 (payments are rejected) |
| Agreement `paymentSummary.status` | `PAID` / `UNPAID` / `PARTIALLY_PAID` | computed over participants with agreed > 0: all PAID, all UNPAID, otherwise partial |
| Agreement `paymentSummary.status` | `NOT_DUE` | nobody has an agreed amount > 0 |

The payment status is independent of the agreement `status` (`active` / `voided`): a voided agreement can legitimately be `PARTIALLY_PAID`. A payment itself is `active` or `voided` (reversed).

## Endpoints

| Method and path | Success | Notes |
| --- | --- | --- |
| `POST /finance/distribution-agreements/:agreementId/payments` | `201` first time, `200` identical replay | Register a payment |
| `GET /finance/distribution-agreements/:agreementId/payments` | `200` | `{ items, paymentSummary }`, not paginated |
| `GET /finance/distribution-payments/:id` | `200` | One payment (live status) |
| `POST /finance/distribution-payments/:id/reversals` | `201` first time, `200` identical replay | Reverse a payment |
| `GET /finance/distribution-agreements/:id` (existing) | `200` | Gains `paymentSummary`, computed live. The immutable creation receipt and its replay do NOT carry it |

### Create body (strict: unknown fields are `400`)

| Field | Rule |
| --- | --- |
| `id` | UUIDv7 generated by the client (idempotency key) |
| `participantMemberId` | UUID of a participant frozen in this agreement |
| `amountMinor` | Integer `1..2147483647` |
| `occurredAt` | Zoned ISO instant with at most 3 fractional digits (when the real payment happened) |
| `note` | Optional, trimmed, at most 1000 characters; blank becomes `null` |
| `createdByMemberId`, `deviceId` | Must equal the validated session headers, otherwise `403` |

The client never sends the agreed amount, balance, currency, context, account or participant name.

### Reversal body

`{ id (UUIDv7), reason (trimmed, 1..1000, not blank), occurredAt (zoned ISO, max 3 fractional digits), createdByMemberId, deviceId }`.

### Response (create, replay and reversal)

```json
{
  "id": "0199...",
  "contextId": "...",
  "agreementId": "0199...",
  "participantMemberId": "...",
  "participantName": "Socio Two",
  "amountMinor": 300,
  "currency": "MXN",
  "occurredAt": "2026-10-05T18:00:00.000Z",
  "receivedAt": "2026-10-09T12:00:00.123Z",
  "note": null,
  "createdBy": { "memberId": "...", "name": "Socio One", "accountId": "...", "deviceId": "..." },
  "status": "active",
  "reversal": null,
  "participantSummary": { "memberId": "...", "memberName": "Socio Two", "agreedMinor": 1000, "paidMinor": 300, "pendingMinor": 700, "status": "PARTIALLY_PAID" },
  "paymentSummary": {
    "status": "PARTIALLY_PAID",
    "agreedMinor": 1500, "paidMinor": 300, "pendingMinor": 1200,
    "hasPayments": true, "paymentCount": 1, "activePaymentCount": 1,
    "participants": [ { "memberId": "...", "memberName": "...", "agreedMinor": 1000, "paidMinor": 300, "pendingMinor": 700, "status": "PARTIALLY_PAID" } ]
  }
}
```

- `participantName` is the name FROZEN in the agreement, not the live member name.
- A voided payment has `status: "voided"` and `reversal: { id, reason, occurredAt, receivedAt, createdBy }`.
- The payment fields are the frozen receipt; `status`, `reversal`, `participantSummary` and `paymentSummary` are live. A replay returns the same frozen fields with the current live ones.
- `paymentSummary.hasPayments` is true when ANY payment row (active or voided) exists for the agreement (the UI uses it to warn before voiding an agreement). `paymentCount` counts all rows, `activePaymentCount` the non-reversed ones.
- `GET .../payments` and `GET /finance/distribution-payments/:id` return payments without `participantSummary`/`paymentSummary` per item; the list adds one top-level `paymentSummary`.
- List order: `occurredAt` desc, then `receivedAt` desc, then `id` desc. The list is intentionally unpaginated (bounded by participants times corrections); growth with repeated corrections is an accepted limitation.

## Errors

| Status | Code | When |
| --- | --- | --- |
| 400 | (validation) | Invalid body, unknown field, bad UUID |
| 401 / 403 | | No session / not a socio, unauthorized device or origin mismatch |
| 404 | | Unknown or foreign agreement, payment, or a member that is not a participant of that agreement (always the same `404`, nothing is disclosed) |
| 409 | `FINANCE_PAYMENT_ID_CONFLICT` | The id was reused with different content, another agreement or account, in another tenant, or (reversals) for another payment |
| 409 | `FINANCE_PAYMENT_AGREEMENT_VOIDED` | Creating a payment on a voided agreement |
| 409 | `FINANCE_PAYMENT_ALREADY_VOIDED` | The payment already has a reversal |
| 422 | `FINANCE_PAYMENT_EXCEEDS_PENDING` | `paid + amount > agreed`; the body also carries `agreedMinor`, `paidMinor`, `pendingMinor` |
| 422 | `FINANCE_PAYMENT_NOTHING_AGREED` | The participant's agreed amount is 0 |
| 422 | `FINANCE_PAYMENT_TIME_INVALID` | `occurredAt` before the agreement `occurredAt` or after the server clock |
| 422 | `FINANCE_PAYMENT_REVERSAL_TIME_INVALID` | Reversal `occurredAt` before the payment `occurredAt` or after the server clock |

## Time rules and clock skew

`occurredAt` is supplied by the client but bounded by the server: it must be at or after the agreement `occurredAt` and at or before the server clock captured while holding the locks (no tolerance, same as agreements). A device clock ahead of the server therefore gets `422 FINANCE_PAYMENT_TIME_INVALID`; the frontend must handle it by asking the user to pick an earlier time. The same bounds apply to a reversal against the payment `occurredAt`.

## Idempotency

The replay lookup runs under the id advisory lock BEFORE every business rule. Consequently a retry after a payment exactly filled the balance returns `200` (not `422`), a retry after the agreement was voided or the payment was reversed returns `200` (not `409`), and a reversal retry after success returns `200`. The fingerprint covers context, account, agreement, participant, amount, instants, note and origin; any difference with the same id is `409 FINANCE_PAYMENT_ID_CONFLICT`. An id that exists in ANOTHER tenant is invisible under row level security; the insert then hits the primary key and is reported as the same `409` without disclosing anything.

## Concurrency model

READ COMMITTED with row locks (the default isolation level; each statement re-reads committed data, so the balance computed after the lock is fresh).

- Create: advisory lock on the payment id (`pg_advisory_xact_lock`), replay lookup, `SELECT ... FOR SHARE` on the agreement row and re-read of its voided state, `SELECT ... FOR UPDATE` on the participant row, THEN the paid sum, the cap check and the insert. The SHARE lock serializes with a concurrent void (which takes `FOR UPDATE` on the agreement): a payment is either committed before the void or rejected with `409 FINANCE_PAYMENT_AGREEMENT_VOIDED`.
- Reversal: advisory lock on the reversal id, read the payment, `FOR UPDATE` on the participant row, `FOR UPDATE` on the payment, then check and insert.
- Both take the participant lock before the payment row, and the void path never takes participant locks, so there is no lock cycle and no retry loop; waiters simply queue. There is no in-process queue.
- The cumulative cap cannot be a CHECK constraint; it is enforced by this serialization and proven by tests (800 against 1000 pending, 12 parallel payments, payment versus reversal, two reversals of one payment, payment versus agreement void).
- Database guards: `amountMinor > 0 and <= 2147483647`, UUIDv7 ids, currency format, note and reason length, `reversal id <> payment id`, one reversal per payment (unique `paymentId`), composite foreign keys to the frozen participant, agreement, member, account and device, `ENABLE` and `FORCE ROW LEVEL SECURITY` with the `tenant_isolation` policy, and `BEFORE UPDATE OR DELETE` triggers that reject any change on both tables. Row locks (`FOR UPDATE`) do not fire UPDATE triggers.

## Isolation from the rest of Finanzas

A payment is not an operating expense. `Expense`, `operatingResult`, margin, sales, contributions, work shifts, reserves, the agreement snapshot and its PDF are NOT modified, and `potentiallyAvailableMinor` is NOT adjusted. Payments are shown separately. An e2e regression test compares `GET /finance/overview` and the agreement and participant rows before and after payments and reversals.

## What is NOT done

- Payment method (cash, transfer...), receipts or PDF of a payment.
- Offline queue: payments are online only.
- Atomic replacement of a payment (the correction is reverse, then pay again).
- Cash or bank balance and reconciliation; no adjustment of the overview.
- Automatic payment, notification or any real movement of money.
- Pagination of the payments list.
- Production migration: `20261010120000_finance_distribution_payments` is applied only when the operator deploys.
